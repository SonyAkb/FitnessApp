# FitQuest — задачи по модулям (команда из 5 человек)

Это карта задач для текущего проекта FitQuest **как он есть в этом репозитории** (`backend-fit-baddy` + `mobile-fit-baddy`), разбитая по 5 модулям/владельцам согласно `CLAUDE.md` и `docs/ARCHITECTURE.md`.

Каждый блок `#### [CODE-N] ...` — это одна задача. Заголовок блока = заголовок issue, всё содержимое под ним = тело issue. Можно копировать по одному блоку прямо в GitHub Issues.

**Легенда статусов** (проверено по коду на момент написания, не по документации):

- ✅ **Готово** — код есть, эндпоинт/логика реально работает.
- 🟡 **Частично** — базовая версия есть, но не покрывает требование полностью (см. пояснение в задаче).
- ⬜ **Не начато** — кода нет.

## Модуль 1 — Аккаунт и расписание (Auth & Schedule)

### Эпик 1.1 — Регистрация, вход, профиль

#### `[ACC-1]` Регистрация пользователя ✅
- Статус: ✅ Готово
- Эпик: Аккаунт и расписание / Регистрация и вход
- Приоритет: Must
- Модуль/роль: Backend — Аккаунт и расписание

**Описание**
Пользователь создаёт аккаунт по email/паролю и получает токены доступа.

**Требования**
- Поля: email, password, display_name.
- Email уникален, пароль хешируется (не хранится в открытом виде).
- В ответ выдаются `access_token` и `refresh_token`.

**Критерии приёмки**
- [x] `POST /api/v1/auth/register` создаёт пользователя и возвращает токены + `user`.
- [x] Повторная регистрация с тем же email возвращает понятную ошибку, а не 500.
- [x] Пароль хранится хешированным (bcrypt).

**Реализация:** `backend-fit-baddy/app/modules/auth/router.py`, `service.py`, `app/core/security.py`.

---

#### `[ACC-2]` Вход и выдача JWT ✅
- Статус: ✅ Готово
- Эпик: Аккаунт и расписание / Регистрация и вход
- Приоритет: Must
- Модуль/роль: Backend — Аккаунт и расписание

**Описание**
Пользователь входит по email/паролю и получает JWT для доступа к защищённым эндпоинтам.

**Критерии приёмки**
- [x] `POST /api/v1/auth/login` проверяет пароль и возвращает `access_token`/`refresh_token`.
- [x] Неверный пароль/email → 401 с понятным сообщением.
- [x] `GET /api/v1/auth/me` возвращает профиль текущего пользователя по Bearer-токену.

---

#### `[ACC-3]` Эндпоинт обновления access-токена по refresh-токену ⬜
- Статус: ⬜ Не начато (инфраструктура частично есть)
- Эпик: Аккаунт и расписание / Регистрация и вход
- Приоритет: Should
- Модуль/роль: Backend — Аккаунт и расписание

**Описание**
`create_refresh_token()` уже существует в `app/core/security.py` и refresh-токен выдаётся при логине/регистрации, но нет эндпоинта, который принимает refresh-токен и выдаёт новый access-токен. Сейчас клиенту, по сути, некуда его передать — токен просто лежит в ответе неиспользуемым.

**Требования**
- Новый эндпоинт `POST /api/v1/auth/refresh` принимает refresh-токен, проверяет `typ=refresh` и срок жизни, выдаёт новый access-токен.
- Просроченный/невалидный refresh-токен → 401.

**Критерии приёмки**
- [ ] Эндпоинт `POST /api/v1/auth/refresh` добавлен и задокументирован в Swagger.
- [ ] Тест: валидный refresh → новый access-токен; протухший/чужой → 401.

#### `[SCH-3]` Повторяющиеся тренировки (RRULE) 🟡
- Статус: 🟡 Частично
- Приоритет: Could
- Модуль/роль: Backend — Аккаунт и расписание

**Описание**
В схеме `ScheduleCreateIn` есть поле `repeat_rule`, но логики разворачивания повторов (создание серии слотов, обработка «только этот / все следующие» при редактировании) нет — поле просто сохраняется как строка.

**Требования**
- Поддержать минимальный набор правил: ежедневно / еженедельно по дням недели / N раз.
- При создании с `repeat_rule` — генерировать серию `ScheduledWorkout` на выбранный горизонт (например, 8 недель вперёд).
- При редактировании/удалении — выбор «только этот слот» или «все в серии».

**Критерии приёмки**
- [ ] Создание слота с `repeat_rule="weekly:mon,wed,fri"` создаёт серию слотов.
- [ ] Удаление одного слота серии не трогает остальные, если выбрано «только этот».

#### `[DEV-5]` Приём и авторизация данных от внешнего устройства по `device_token` ⬜
- Статус: ⬜ Не начато
- Приоритет: Could (готовит почву под будущий `pi-fit-baddy`)
- Модуль/роль: Backend — Devices

**Описание**
`device_token` генерируется при регистрации, но никогда не проверяется — все текущие эндпоинты телеметрии работают через JWT пользователя, а не через устройство. Нет эндпоинта, куда внешний производитель данных (будущий Pi) мог бы стучаться напрямую.

**Требования**
- Эндпоинт `POST /api/v1/devices/{device_id}/telemetry`, авторизация через заголовок с `device_token` (не пользовательский JWT).
- Проверка, что `device_id` принадлежит существующему устройству и токен совпадает.

**Критерии приёмки**
- [ ] Запрос с верным `device_token` сохраняет точку и транслирует её тем же путём, что и `simulate`.
- [ ] Запрос с неверным/отсутствующим токеном → 401.
