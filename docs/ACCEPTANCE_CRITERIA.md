# Критерии приемки FitQuest

Соответствие пользовательским историям из `docs/USER_STORIES.md`.

---

## 1. Регистрация и цель

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC1.1 | Регистрация успешна | Пользователь вводит `email`, `password` (8+ символов), `display_name` | `201` + JWT + `user.goal = null` |
| AC1.2 | Регистрация дубликата | Пользователь с тем же `email` пытается зарегистрироваться повторно | `409 Conflict` с описанием |
| AC1.3 | Невалидный пароль | `password` короче 8 символов | `422 Validation Error` |
| AC1.4 | Создание питомца | После успешной регистрации | Backend создает `Pet` со `xp=0`, `level=1`, `mood="idle"` |
| AC1.5 | Установка цели | Пользователь после регистрации отправляет `PATCH /profile` с `goal` | `200` + `goal` сохранен + возвращен `GET /auth/me` с заполненным `goal` |
| AC1.6 | Редкая отправка | Нет повторной отправки `goal` при повторном `GET /auth/me` | Возвращается тот же `goal`, не обнуляется |

## 2. Вход и тренировка на сегодня

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC2.1 | Успешный вход | Правильные `email` и `password` | `200` + JWT + `user` |
| AC2.2 | Неверные учётные данные | Неверный `email` или `password` | `401 Unauthorized` |
| AC2.3 | Получение расписания | `GET /schedule?from=2026-09-17&to=2026-09-17` | `200` + `ScheduleItem[]` (для заданной даты) |
| AC2.4 | Пустое расписание | Нет слотов на текущую дату | `200 []` (пустой массив, не ошибка) |
| AC2.5 | Подгрузка плана | У слота есть `plan_id`, вызов `GET /workouts/plans/{id}` | `200` + `WorkoutPlan` с упражнениями |
| AC2.6 | План без упражнений | План создан, но без `exercises` | `200` с пустым массивом `exercises[]` |

## 3. Создание плана и запись в календарь

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC3.1 | Создание плана | `POST /workouts/plans` с `name` и `exercises[]` (2+ упражнения) | `201` + `WorkoutPlan.id` + упражнения сохранены |
| AC3.2 | Создание слота | `POST /schedule` с `plan_id` и `starts_at` (например, завтра 18:00) | `201` + `ScheduleItem` с `status="planned"` |
| AC3.3 | Валидация временных рамок | `starts_at` в прошлом (например, вчера) | `422 Validation Error` |
| AC3.4 | Валидация `plan_id` | Не существующий `plan_id` | `404 Not Found` |
| AC3.5 | Редактирование слота | `PATCH /schedule/{id}` с новым `starts_at` | `200` + обновлённый `ScheduleItem` |
| AC3.6 | Удаление слота | `DELETE /schedule/{id}` | `204 No Content` |
| AC3.7 | Удаление несуществующего | `DELETE /schedule/999` | `404 Not Found` |

## 4. Выполнение тренировки: чек-лист и таймер

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC4.1 | Старт сессии | `POST /workouts/sessions` с `plan_id` | `201` + `session_id`, `status="in_progress"`, `started_at` |
| AC4.2 | Отсутствие `plan_id` | Отправить без `plan_id` | `422 Validation Error` (если поле обязательное в MVP) |
| AC4.3 | Локальный таймер | Таймер на телефоне (не обращается к API каждую секунду) | `200` без ошибок, таймер работает локально |
| AC4.4 | Повторный старт | Попытка `POST /sessions` для уже `in_progress` плана | Допустимо: создать новую сессию (можно `409` если запрещено) — **согласовать** |
| AC4.5 | Завершение без_DURATION | `POST /sessions/{id}/complete` без тела | `200` + `duration_seconds` рассчитан по `completed_at - started_at` |
| AC4.6 | Завершение с_DURATION | `POST /sessions/{id}/complete` с `duration_seconds` | `200` + `duration_seconds` = переданное значение |

---

## 5. Завершение тренировки → реакция питомца

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC5.1 | XP начисляется | Завершение тренировки | `xp_awarded` в ответе `complete` (минимум `+10` для MVP) |
| AC5.2 | Обновление питомца | `GET /pet` после завершения | `xp` увеличен на `xp_awarded` |
| AC5.3 | Повышение уровня | `xp >= xp_to_next_level` | `level` увеличен, `xp_to_next_level` пересчитан (например, `xp_to_next_level = level * 100`) |
| AC5.4 | Настроение питомца | После завершения | `mood = "happy"` или `mood = "level_up"` (если был level-up) |
| AC5.5 | Стриск не сбивается | Завершение тренировки в тот же день | `streak_days` не уменьшается (если день не пропущен) |
| AC5.6 | Пропуск слота | `POST /schedule/{id}/miss` | `status = "missed"`, `WorkoutMissed` событие |
| AC5.7 | Реакция на пропуск | `GET /pet` после пропуска | `mood` ухудшается (`sad` или `neutral`), `energy` снижается |
| AC5.8 | Дублирующее завершение | `POST /sessions/{id}/complete` второй раз для той же сессии | `409 Conflict` (сессия уже `completed`) |

## 6. Просмотр XP, уровня, настроения и стрика

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC6.1 | Состояние питомца | `GET /pet` | `200` + `xp`, `xp_to_next_level`, `level`, `energy`, `mood`, `streak_days` |
| AC6.2 | Энергия в диапазоне | `energy` всегда | `0 <= energy <= 100` |
| AC6.3 | Валидный уровень | `level` всегда | `level >= 1` (минимум 1 для новых пользователей) |
| AC6.4 | Валидный XP | `xp` всегда | `xp >= 0` |
| AC6.5 | Стриск в дашборде | `GET /dashboard/summary` | `current_streak_days` совпадает с `streak_days` из `/pet` |
| AC6.6 | Отсутствующий питомец | Пользователь без `Pet` (теоретически) | `GET /pet` создаёт питомца с `201` или `200` с `default values` |

## 7. Живой пульс и шаги (симулятор)

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC7.1 | Регистрация устройства | `POST /devices/register` с `device_id` и `kind="simulator"` | `201` + `status="active"` |
| AC7.2 | Повторная регистрация | Тот же `device_id` + `user_id` | `200` (idempotent) или `409` — **согласовать** |
| AC7.3 | Генерация точки | `POST /telemetry/simulate` без тела | `201` + `TelemetryDTO` с `source="simulator"`, валидными значениями |
| AC7.4 | Валидация значений | `steps < 0`, `heart_rate < 0`, `calories < 0` | `422 Validation Error` |
| AC7.5 | Получение последней точки | `GET /telemetry/latest` | `200` + `TelemetryDTO` (последняя точка текущего пользователя) |
| AC7.6 | Нет точек | Новых данных не было | `404 Not Found` (не `200` с `null` или `200` с пустым объектом) |
| AC7.7 | История телеметрии | `GET /telemetry/history?from=...&to=...` | `200` + `TelemetryDTO[]` за период |
| AC7.8 | WebSocket подключение | `WS /telemetry/ws?token=...` | Подключение устанавливается, сервер шлёт `TelemetryDTO` при появлении новых точек |
| AC7.9 | Симуляция без регистрации | `POST /telemetry/simulate` без `POST /devices/register` | **Минимум MVP:** допустимо (один POST создаёт и устройство, и точку) |

## 8. Недельный дашборд и история

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC8.1 | Сводка за неделю | `GET /dashboard/summary?period=week` | `200` + агрегированные поля (не сырые копии сессий) |
| AC8.2 | Поля сводки | Обязательные поля в ответе | `total_workouts`, `completed_workouts`, `missed_workouts`, `current_streak_days`, `xp`, `level`, `companion_mood`, `steps_7d` |
| AC8.3 | История тренировок | `GET /workouts/history?limit=20&offset=0` | `200` + `items[]` с сокращённой информацией по сессиям |
| AC8.4 | Пагинация истории | `offset` > количества | `200` + пустой `items[]` (не ошибка) |
| AC8.5 | Телеметрия за период | `GET /telemetry/history?from=...&to=...` | `200` + точки за период, включая `source` |
| AC8.6 | История с пустым периодом | `GET /workouts/history` (без параметров) | `200` + последние `limit` (default 20) |

## 9. Уведомления

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC9.1 | Уведомление после complete | Пользователь завершает тренировку | Backend создаёт `Notification` с `kind="workout_completed"` |

| AC9.3 | Список уведомлений | `GET /notifications` | `200` + `Notification[]`, новые сверху |
| AC9.4 | Список непрочитанных | `GET /notifications?unread_only=true` | `200` + только `is_read=false` |
| AC9.5 | Пометка как прочитанное | `POST /notifications/{id}/read` | `200` + `is_read=true` |
| AC9.6 | Пропуск уведомления | Нет `POST /notifications/{id}/read` | `is_read` остаётся `false` |
| AC9.7 | Пустой центр | Нет уведомлений | `200 []` (пустой массив) |
| AC9.8 | Количество | Максимум в списке | Указывать `limit` (например, 50 последних) |

## 12. Офлайн / обрыв WS: последнее известное + статус

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC12.1 | Живой WS | WebSocket работает, сервер присылает точки | Точки поступают в реальном времени, статус «онлайн» |
| AC12.2 | Обрыв WS | WebSocket падает | Клиент получает `onWsDisconnected`, статус меняется на «офлайн» |
| AC12.3 | Fallback на REST | После обрыва WS → `GET /telemetry/latest` | `200` + последняя точка (если есть в БД) |
| AC12.4 | Нет точки в БД | Клиент запросил после запуска, до первой точки | `404`, клиент показывает «нет данных» |
| AC12.5 | Локальный кэш | REST тоже недоступен | Клиент показывает последнюю известную точку из SharedPreferences/Room |
| AC12.6 | Статус сети | В UI отображается | «онлайн» / «офлайн, последнее известное» с датой точки |

## Общие критерии (Cross-Cutting)

| № | Критерий | Сценарий | Ожидаемое поведение |
|---|----------|----------|---------------------|
| AC-G1 | Аутентификация | Все защищённые эндпоинты без JWT | `401 Unauthorized` |
| AC-G2 | Проверка владения | `GET /pet` другого пользователя (через подмену токена) | `403 Forbidden` (если реализован) или `200` own data (базовый MVP допустимо без проверки) |
| AC-G3 | Валидация токена | Просроченный JWT | `401 Unauthorized` |
| AC-G4 | Swagger документация | Все эндпоинты видны в `/docs` | Контракты соответствуют `API_CONTRACT.md` |
| AC-G5 | Точность данных | `steps`, `heart_rate`, `calories` в `TelemetryDTO` | Валидные значения (без `NaN`, `Infinity`) |
| AC-G6 | ISO-8601 время | Все даты в API | `2026-09-17T18:00:00Z` (UTC) |
| AC-G7 | HTTP статусы | Все ошибки | `4xx` для клиентских, `5xx` для серверных |
| AC-G8 | Согласованность XP | `xp` в `/pet` и `/dashboard` | Сумма `xp_awarded` из завершенных сессий = текущий `xp` |
