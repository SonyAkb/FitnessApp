# Wearable Bridge Prototype — задачи по модулям (команда из 4 человек)

Отдельный прототип (для другого преподавателя): Raspberry Pi с датчиками → сервер-мост → нативное Android-приложение, плюс AI-модуль (RAG, обучается в Google Colab). В этой итерации Pi **не физическое устройство** — это обычный Linux-процесс, который вместо реального I2C сам генерирует правдоподобные показания датчиков и подсчитывает шаги по синтетическому сигналу. Реальное железо (MAX30102/MPU6050/GPIO) — следующий шаг после защиты этого прототипа, не входит в текущий объём.

Команда — 4 роли:
1. **Sensor Node** (симулированный Pi) — Person A.
2. **Bridge Server** (мост, хранение, авторизация устройств) — Person B.
3. **Android App** — Person C.
4. **AI/RAG** — Person D.

Формат задач такой же, как в `docs/TASKS_FITQUEST_TEAM5.md`: один блок `#### [CODE-N] ...` = одна GitHub issue. Пометка ✅ означает, что задача уже закрыта — как правило, потому что аналогичный код существует в `backend-fit-baddy`/`mobile-fit-baddy` этого же репозитория (модуль FitQuest Devices) и переносится в этот прототип с адаптацией, а не пишется с нуля.

**Легенда статусов:**
- ✅ **Готово** — рабочий код есть (либо в этом прототипе, либо переносится из FitQuest почти без изменений).
- 🟡 **Частично** — есть черновой аналог, но не покрывает требование прототипа полностью.
- ⬜ **Не начато** — кода нет вообще, писать с нуля.

## Роль 1 — Sensor Node (симулированный Raspberry Pi)

### Эпик S1 — Генерация синтетических показаний

#### `[SENS-1]` Симуляция сигнала акселерометра + подсчёт шагов по пикам ускорения ⬜
- Статус: ⬜ Не начато
- Приоритет: Must
- Роль: Sensor Node

**Описание**
Ядро задания — не просто выдавать случайное число шагов, а сгенерировать синтетический сигнал ускорения (например, синусоида + шум, имитирующая ходьбу) и **реально посчитать шаги алгоритмом детекции пиков**, как это делал бы код на реальном MPU6050. FitQuest сейчас использует `random.randint(4000, 12000)` без какой-либо сигнальной модели — это не подходит для данного задания, где требуется именно алгоритм подсчёта.

**Требования**
- Генератор временного ряда ускорения с частотой, похожей на реальные шаги (~1.5–2.5 Гц).
- Алгоритм детекции пиков (порог + минимальный интервал между пиками, чтобы не считать шум как шаг).
- Функция `count_steps(signal_window) -> int`, покрытая unit-тестом на синтетическом сигнале с известным числом пиков.

**Критерии приёмки**
- [ ] На тестовом сигнале с заранее известным количеством пиков алгоритм даёт точный (±1) результат.
- [ ] Логика инкапсулирована в отдельном модуле, не завязана на конкретный I2C-драйвер — чтобы позже подставить реальные показания с MPU6050 без переписывания алгоритма.

---

#### `[SENS-2]` Правдоподобная симуляция пульса (с динамикой, не чистый random) 🟡
- Статус: 🟡 Частично (идея генерации переносится из FitQuest, но там нет временной динамики)
- Приоритет: Must
- Роль: Sensor Node

**Описание**
FitQuest (`backend-fit-baddy/app/modules/devices/service.py::generate_sample`) генерирует пульс как `random.randint(62, 145)` на каждый тик — реалистичный пульс не скачет так резко между соседними точками. Для этого прототипа нужна модель с плавным дрейфом (например, случайное блуждание вокруг базового уровня + всплески при «нагрузке»).

**Критерии приёмки**
- [ ] Соседние по времени значения пульса отличаются не более чем на заданный шаг (например, ±5 уд/мин).
- [ ] Есть режим «нагрузка/отдых», влияющий на базовый уровень пульса (даже вручную переключаемый флагом, не обязательно от реальной активности).

### Эпик S2 — Sensor Node как отдельный сервис

#### `[SENS-3]` REST/WS-сервис на узле-«Pi», отдающий данные мосту ⬜
- Статус: ⬜ Не начато
- Приоритет: Must
- Роль: Sensor Node

**Описание**
В FitQuest симуляция происходит **внутри самого бэкенда** (мост сам себе генерирует точки). В этом задании требуется, чтобы «Pi» был отдельным процессом со своим FastAPI-приложением, который **публикует** данные мосту, а не наоборот. Это принципиально другая схема связи, писать с нуля.

**Требования**
- Отдельное FastAPI-приложение (`pi-node/` или аналогично), с собственным `main.py`, независимым от `backend-fit-baddy`.
- Периодическая генерация точки (`SENS-1` + `SENS-2`) и отправка её на bridge-эндпоинт (`BRIDGE-3`) по HTTP.
- Возможность запускать несколько экземпляров (несколько «устройств») с разными `device_id`.

**Критерии приёмки**
- [ ] Sensor Node запускается независимым процессом/контейнером и не падает при недоступности моста (ретраи с backoff).
- [ ] Логирует каждую отправленную точку локально (для отладки без доступа к мосту).

---

#### `[SENS-4]` Профили «тестовый» и «боевой» набор данных на одном узле ⬜
- Статус: ⬜ Не начато
- Приоритет: Should
- Роль: Sensor Node

**Описание**
Поскольку реальных датчиков нет, «боевой» режим — это тоже симуляция, но с другим профилем генерации (например, более «шумной»/приближенной к реальным сенсорам моделью, помечаемой `source=raspberry_pi`), а тестовый — упрощённый (`source=simulator`). Клиент и мост не должны знать о разнице — только значение `source` в DTO отличается.

**Критерии приёмки**
- [ ] Флаг/переменная окружения переключает профиль генерации без изменения формата отправляемых данных.
- [ ] В обоих профилях DTO идентичен по структуре полям (`device_id, steps, heart_rate, calories, timestamp, source`).

#### `[BRIDGE-3]` Приём точек телеметрии от устройства (ingestion endpoint) ⬜
- Статус: ⬜ Не начато — **в FitQuest этого эндпоинта нет вообще**, там мост сам себе генерирует данные
- Приоритет: Must
- Роль: Bridge Server

**Описание**
Ключевая недостающая часть по сравнению с уже существующим кодом: нужен эндпоинт, куда Sensor Node (реальный или симулированный) отправляет свежую точку, а мост её сохраняет и раздаёт дальше (REST + WS-подписчикам).

**Требования**
- `POST /devices/{device_id}/telemetry` — принимает `{steps, heart_rate, calories, timestamp, source}`.
- После сохранения — рассылка всем открытым WS-соединениям пользователя, владеющего устройством.

**Критерии приёмки**
- [ ] Точка, отправленная на этот эндпоинт, немедленно появляется в `GET /telemetry/latest` и у подключённых по WS клиентов.
- [ ] Отклонение точки с явно некорректными значениями (например, отрицательные шаги) — 422.

#### `[BRIDGE-4]` Авторизация устройств по `device_token` ⬜
- Статус: ⬜ Не начато — в FitQuest токен генерируется, но нигде не проверяется
- Приоритет: Must
- Роль: Bridge Server

**Описание**
`device_token` в FitQuest создаётся при `POST /devices/register`, но ни один эндпоинт его не проверяет — вся авторизация телеметрии там идёт через пользовательский JWT. Для этого прототипа устройство (Pi/Sensor Node) не имеет пользовательской сессии — только свой токен, поэтому проверка обязательна.

**Требования**
- `BRIDGE-3` принимает токен устройства в заголовке (например, `X-Device-Token`), не JWT.
- Проверка: токен принадлежит `device_id` из пути, устройство не отозвано/не заблокировано.

**Критерии приёмки**
- [ ] Запрос с верным токеном своего устройства — 201.
- [ ] Запрос с токеном другого устройства или без токена — 401/403, а не тихий успех.

## Роль 4 — AI/RAG

### Эпик AI1 — Данные и retrieval

#### `[AI-1]` Подготовка данных для RAG (история активности как контекст) ⬜
- Статус: ⬜ Не начато
- Приоритет: Must
- Роль: AI/RAG

**Описание**
В отличие от FitQuest, где рекомендация — простое правило по количеству тренировок, здесь требуется retrieval-augmented подход: рекомендация строится с опорой на релевантные фрагменты истории пользователя (тренировки, показатели устройства), а не только на одно агрегированное число.

**Требования**
- Выгрузка/подготовка выборки данных из bridge (историю тренировок + телеметрию) в формат, пригодный для индексации (текстовые «карточки события»: дата, тип, показатели).
- Скрипт подготовки данных запускается в Google Colab.

**Критерии приёмки**
- [ ] Есть репрезентативный датасет (синтетический — ок, реальные пользователи не обязательны) с описанием формата.
