# Промпт: модуль устройства (Raspberry Pi) для FitQuest

Ты помогаешь разработать серверную часть носимого модуля на Raspberry Pi для фитнес-приложения FitQuest. Ниже контекст, требования и критерии приёмки. Главное требование: **код, написанный и протестированный на Mac/Linux с эмуляцией, должен без изменений работать на реальной Raspberry Pi с подключёнными датчиками.** Менять при переезде допускается только переменные окружения.

---

## 1. Контекст

- Android-клиент (Java) получает от устройства пульс и шаги по REST/WebSocket.
- Устройство: Raspberry Pi, Raspberry Pi OS (Linux), Python 3.11+.
- Датчики по I2C: акселерометр **MPU6050** и пульсометр **MAX30102**.
- Разработка идёт на машинах без платы (Mac, в том числе Apple Silicon, и Linux), поэтому нужна эмуляция. Эмулируем **шину и чипы на уровне регистров**, а не готовые значения.

## 2. Что нужно сделать

Реализовать Python-сервис со слоями (сверху вниз):

1. **API (FastAPI)** — контракт в разделе 5.
2. **Сервисы** — подсчёт шагов, оценка пульса, фоновый опрос датчиков.
3. **Драйверы** — `Mpu6050`, `Max30102`. Работают с абстрактной шиной, ничего не знают об эмуляции.
4. **Шина** — `smbus2.SMBus(1)` на плате или `FakeSMBus` в эмуляции. Выбор в одной функции по переменной `SENSOR_MODE` (`real` / `mock`, по умолчанию `mock`).
5. **Виртуальные чипы** — `VirtualMPU6050`, `VirtualMax30102`: карта регистров, поведение как у железа.
6. **Генераторы сигналов** — синтетические данные для виртуальных чипов (сценарии, проигрывание CSV).

Структура репозитория:

```
device/
  api/         # FastAPI, схемы ответов
  services/    # step_counter.py, heart_rate.py, sampler.py
  drivers/     # mpu6050.py, max30102.py
  bus/         # factory.py, fake_smbus.py
  virtual/     # mpu6050.py, max30102.py, signals.py, scenarios.py
  tests/
  data/        # записи с реальных датчиков (CSV)
```

## 3. Обязательные правила переносимости (mock → real)

1. Драйверы и сервисы **одинаковы** в обоих режимах. Единственная точка ветвления на `SENSOR_MODE` — `bus/factory.py`.
2. Драйвер принимает шину через конструктор и использует только методы, которые есть и у `smbus2.SMBus`, и у `FakeSMBus`: `write_byte_data(addr, reg, val)`, `read_byte_data(addr, reg)`, `read_i2c_block_data(addr, reg, length)`.
3. Аппаратные библиотеки (`smbus2`, `gpiozero`, `RPi.GPIO`) импортируются **лениво**, внутри веток `real`. В режиме `mock` модуль не должен падать при импорте на Mac.
4. Для GPIO использовать `gpiozero`. В тестах: `GPIOZERO_PIN_FACTORY=mock`. Прямой `RPi.GPIO` не использовать.
5. Никаких «умных» обходов в эмуляции. Если драйвер забыл вывести чип из сна, неверно задал диапазон или адрес, виртуальный чип обязан дать ту же ошибку или те же данные, что и железо (нули, `OSError`, переполнение FIFO).
6. Время берётся из внедряемого объекта часов (`Clock` с методом `now()`). В тестах часы управляемые, в рантайме реальные (`time.monotonic`). Никаких `time.sleep` в логике, которая тестируется.
7. Ничего не хардкодить под Mac: пути, номер шины (`I2C_BUS=1`), адреса и пороги идут из конфигурации с разумными значениями по умолчанию.
8. Все параметры алгоритмов (пороги шагов, полосы фильтра) вынести в один конфиг. Они будут подбираться на реальном железе.

## 4. Аппаратные факты

### MPU6050 (I2C 0x68)

| Регистр | Адрес | Примечание |
|---|---|---|
| ACCEL_CONFIG | 0x1C | диапазон ±2/4/8/16 g |
| ACCEL_XOUT_H | 0x3B | 6 байт: X, Y, Z, старший байт первым, знаковые 16 бит |
| PWR_MGMT_1 | 0x6B | **после включения питания чип в режиме сна**, драйвер обязан его разбудить |
| WHO_AM_I | 0x75 | возвращает 0x68, драйвер проверяет при инициализации |

### MAX30102 (I2C 0x57)

| Регистр | Адрес |
|---|---|
| INT_STATUS | 0x00 |
| INT_ENABLE | 0x02 |
| FIFO_WR_PTR | 0x04 |
| OVF_COUNTER | 0x05 |
| FIFO_RD_PTR | 0x06 |
| FIFO_DATA | 0x07 |
| FIFO_CONFIG | 0x08 |
| MODE_CONFIG | 0x09 |
| SPO2_CONFIG | 0x0A |
| LED1_PA / LED2_PA | 0x0C / 0x0D |
| REV_ID / PART_ID | 0xFE / 0xFF |

### Что нужно сверить с даташитом (не угадывать)

Эти значения не подтверждены, возьми их из официальных даташитов MPU-6000/6050 и MAX30102 и пометь в коде комментарием со ссылкой на раздел:

- чувствительность акселерометра (LSB/g) для каждого диапазона и биты выбора диапазона в ACCEL_CONFIG;
- значение PART_ID и битовые поля MODE_CONFIG, SPO2_CONFIG, FIFO_CONFIG, INT_STATUS;
- формат отсчёта FIFO (число байт на канал, сколько бит значимых, порядок каналов в режиме SpO2);
- как работают указатели FIFO (циклический буфер, 32 слота, поведение при переполнении).

Если в чём-то не уверен, не придумывай, а оставь `TODO(datasheet)` и напиши, чего не хватает.

## 5. API (контракт не менять)

```
GET /device/status
    → {"connected": true, "battery": 82, "mode": "mock"}

GET /device/vitals/current
    → {"heart_rate": 76, "steps": 4213, "timestamp": "2026-10-14T12:00:00Z"}

GET /device/vitals/history?from=...&to=...
    → [{"heart_rate": 74, "steps": 4100, "timestamp": "..."}, ...]

WS  /device/stream
    → JSON с теми же полями, раз в 1–2 секунды
```

- Время в ISO 8601 UTC.
- `battery` для эмуляции фиксированное или медленно убывающее, на плате берётся из конфигурации (датчика заряда может не быть).
- Если датчик не отвечает, API возвращает `connected: false` и не падает.
- История хранится в памяти с ограничением размера (кольцевой буфер). Постоянное хранение делает сервер-мост.

## 6. Виртуальные чипы

**Общие требования:** собственная карта регистров, значения при включении питания как в даташите, недоступное при сне чипа, неверный адрес на шине даёт `OSError(121, "Remote I/O error")`.

**VirtualMPU6050:**
- после старта PWR_MGMT_1 в состоянии сна, данные читаются как нули, пока драйвер не разбудит чип;
- диапазон берётся из ACCEL_CONFIG и влияет на масштаб значений;
- регистры данных обновляются из генератора сигнала в момент чтения по часам.

**VirtualMax30102:**
- FIFO с указателями WR/RD и счётчиком переполнения;
- новые отсчёты «производятся» по времени с частотой из SPO2_CONFIG, число накопленных отсчётов считается по часам;
- чтение FIFO_DATA отдаёт байты в формате из даташита и сдвигает RD_PTR;
- при невычитанном FIFO растёт OVF_COUNTER;
- сигнал — синтетическая пульсовая волна (постоянная составляющая, пульсовая компонента с заданной ЧСС, шум).

**Сигналы и сценарии:**
- сценарий — список сегментов: `покой`, `ходьба`, `бег`, `восстановление`, у каждого длительность, шаги в минуту, ЧСС, уровень шума;
- ходьба: сигнал вокруг 1 g с периодическими пиками на частоте шагов;
- плюс проигрыватель CSV с реальными записями (формат: время, x, y, z / время, ir, red).

## 7. Алгоритмы

- **Шаги:** модуль вектора ускорения, вычитание гравитации или фильтр, сглаживание, поиск пиков с порогом и минимальным интервалом между шагами. Состояние накапливается между вызовами. Алгоритм должен работать на потоке отсчётов, а не на готовом массиве.
- **Пульс:** убрать постоянную составляющую ИК-канала, полосовой фильтр около 0.5–4 Гц, поиск пиков, ЧСС по медианному интервалу за скользящее окно. Если сигнал слабый или шумный, возвращать `null`, а не выдуманное число.
- Параметры настроены на синтетику, но должны легко переопределяться конфигом для реальных данных.

## 8. Тесты (pytest, запускаются без железа)

- Драйвер MPU6050: WHO_AM_I проходит; спящий чип без пробуждения не отдаёт данных; смена диапазона меняет масштаб; неверный адрес даёт ошибку.
- Драйвер MAX30102: инициализация настраивает регистры; чтение FIFO корректно разбирает байты; переполнение отражается в счётчике.
- Шаги: сценарий «ходьба N шагов» даёт N ± допуск; покой даёт 0.
- Пульс: сценарий с ЧСС 72 даёт 72 ± 3; слабый сигнал даёт `null`.
- API: все эндпоинты отвечают по контракту в режиме `mock`.
- Переносимость: тест, который подменяет `FakeSMBus` объектом с тем же интерфейсом и проверяет, что драйверы работают без изменений.

## 9. Критерии приёмки

1. `SENSOR_MODE=mock pytest` проходит на Mac без платы и без установленных `RPi.GPIO` / `smbus2`.
2. `SENSOR_MODE=real` на Raspberry Pi запускает тот же код: меняется только шина и пины, правки драйверов и сервисов не нужны.
3. Ни в драйверах, ни в сервисах нет проверок на режим эмуляции.
4. Любое значение, которое не удалось подтвердить по даташиту, помечено `TODO(datasheet)`.
5. Есть `README` модуля: как запустить в mock, как запустить на Pi, схема подключения (адреса, номер шины, пины), как записать CSV с реальных датчиков.
